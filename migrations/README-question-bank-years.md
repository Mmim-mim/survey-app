# Question Bank fiscal years

This file is a run-once migration, not an application startup step. A read-only audit
of the locally configured Aiven `survey_app` found its columns, tables, indexes, foreign
keys and lock row already installed. Do not rerun it there. The user confirmed that
Render and localhost use matching DB_HOST, DB_PORT (25248), and DB_NAME (survey_app).
Treat this as a shared Production database; Render's running connection has not been
independently fingerprinted. A different target needs its own read-only preflight.
Never run development writes on this shared database.

## Observed schema and preflight

The source uses these columns (existing SQL types/indexes are not provided in the repo):

- `survey_sections`: id, section_key, title, description, sort_order, is_active, created_at.
- `survey_question_categories`: id, section_id, title, description, sort_order, is_active, created_at.
- `survey_question_groups`: id, category_id, title, description, sort_order, is_active, created_at.
- `question_bank`: id, group_id (legacy rows may be NULL), category, question_text,
  used_in_label, datalist_id, question_type, status, sort_order, created_at.
- `survey_forms`: fiscal_year and form_json, alongside project/owner metadata.
- `submissions`: form_id and payload_json, alongside response metadata.
- No separate relationship/mapping table is referenced by the current application.

On an authorized disposable database restored from a backup, first inspect:

```sql
SHOW CREATE TABLE survey_sections;
SHOW CREATE TABLE survey_question_categories;
SHOW CREATE TABLE survey_question_groups;
SHOW CREATE TABLE question_bank;
SHOW INDEX FROM survey_question_categories;
SHOW INDEX FROM survey_question_groups;
SHOW INDEX FROM question_bank;

SELECT g.id, g.category_id
FROM survey_question_groups g LEFT JOIN survey_question_categories c ON c.id=g.category_id
WHERE c.id IS NULL;
SELECT q.id, q.group_id
FROM question_bank q LEFT JOIN survey_question_groups g ON g.id=q.group_id
WHERE q.group_id IS NOT NULL AND g.id IS NULL;
```

All participating tables must use InnoDB. Verify generated IDs and created_at defaults
match the existing INSERT statements. A global UNIQUE constraint on a title, question
text or datalist could prevent cloning: stop and review the actual DDL; do not drop
an unknown index or infer its replacement. Additional mandatory columns also require
review before running. The supplied migration deliberately does not alter existing ID types.

## Before / after and rollout

1. Back up the test schema and data and record row counts and highest IDs.
2. Run `001-question-bank-fiscal-years.sql` ONCE on that test copy. DDL is not atomic;
   if a statement fails, inspect which statements completed instead of blindly rerunning.
3. New tables: `question_bank_years` (unique fiscal_year, source_fiscal_year), and
   `question_bank_write_lock` (one serialization row). Categories, Groups, Questions
   receive nullable fiscal_year with an index/FK to the year registry. Questions also
   receive nullable deleted_at for non-destructive deletion.
4. Existing rows remain NULL-year Legacy. No titles/IDs/relationships/form JSON/submission
   payloads are rewritten. This is the backfill policy: preserve originals rather than
   guessing the historical fiscal year of each template.
5. Start the changed application against the TEST database only. Open Admin Questions
   and create the intended first year (for example 2570; the application does not assume it).
   This clones Legacy into that explicit year. It does not move legacy records.
6. A later year clones the greatest smaller registered year with structure or question
   data. If no smaller year exists, it fails (Legacy bootstrap is only for the first year).
   Empty years are skipped; inactive questions and sort/status metadata are preserved.
7. Verify new IDs and FK mappings and compare original row counts/content. Run the tests
   and manual checklist below before considering a separate Production rollout.

## Clone and identities

All bank mutations and Clone take an InnoDB row lock in one transaction. The entire
Category -> Group -> Question copy commits together. Orphan relationships cause rollback.
IDs are generated by existing auto-increment columns; maps remap each parent FK.
Group-generated datalist IDs are remapped. Stable project keys such as dept_name stay
the same but their option rows are isolated by year. Ungrouped legacy questions retain
their stored datalist identity. Public bank/structure reads apply a verified compatibility
map for six legacy aliases, requiring an exact, unique Category/Group match in the same
year. This is an in-memory mapping, not an UPDATE or a Clone transaction change.
Unknown, renamed or ambiguous matches remain ungrouped. Project dropdowns are excluded.

Sections are shared and retain immutable section_key. They are NOT yearly copies.
Section Snapshot remains independent from annual question templates.
Deleting questions sets deleted_at and inactive status; deleting Category/Group disables
the row. Existing references remain intact. Inactive Category/Group rows can be re-enabled
in Admin Structure. Deleted questions are not copied into later years.

## APIs

- GET `/api/question-bank/years`; POST `/api/admin/question-bank/years` with fiscal_year.
- Existing admin questions/options, active bank and structure/form GET APIs now accept
  fiscal_year. Omitted/`legacy` means only NULL-year data, never all years or latest fallback.
- POST/PUT/DELETE admin questions scope the ID to the selected year. PUT is new.
- Category/Group CRUD is year-scoped; Admin Structure has its own synchronized selector.
- Create/Edit form validates references when question_bank_fiscal_year is non-NULL.

## Form behavior and compatibility

- Create derives fiscal_year and the bank year from start_date using the Thai fiscal
  year (October 1 through September 30). There is no visible year selector. Crossing a
  fiscal-year boundary confirms clearing current question/project choices before loading
  the new bank. Missing years never fall back to Legacy. Save is blocked after load errors;
  late responses cannot overwrite a newer load.
- `form_json.question_bank_fiscal_year` records the template source year. Text and IDs
  remain in the existing section2_models snapshot. fiscal_year is still written to survey_forms.
- Edit/Copy preserve the saved fiscal year and validate it against start_date. Optional
  suggestions use the year calculated from that date; saved question_bank_fiscal_year
  remains the template reference marker. No current bank text replaces saved content. Copy regenerates
  questionId using the existing code and retains questionBankId. A custom question retains null.
- Legacy forms without the marker keep their question snapshots; optional suggestions
  also use start_date. Create/Edit/Copy still require valid dates and consistent fiscal years;
  no stored dates are automatically repaired. For respondent reads/submissions only,
  persisted Legacy forms without a date in either location and without the
  question_bank_fiscal_year field keep the former calendar-year policy. The server
  assigns the current Bangkok calendar year + 543 and source legacy_calendar_year.
  Modern forms with missing dates, malformed dates, and dated forms with conflicting
  years remain errors. Missing/deleted legacy bank records alone do not block snapshots.
- Project dropdown values missing from the live bank are preserved when editing/copying.
- New submissions get fiscal_year and fiscal_year_source="form_start_date" from server
  validation of the saved form; browser-supplied years are not authoritative. No old
  submission payload is updated. Legacy report fallbacks and all score calculations remain
  unchanged. The dashboard's existing
  text lookup is restricted to Legacy so annual copies cannot change legacy lookup ordering.
  New submissions consistently use their saved year in Dashboard/Public/Strategy reports.
  Per-form Result continues to combine responses by form_id, including mixed-year responses.

## Verification and rollback

Run all `tests/*.test.js` with Node's test runner (expand the file list in PowerShell).
Run `tests/browser-question-bank.cjs` separately with PLAYWRIGHT_MODULE pointing to an
installed Playwright package and BROWSER_CHANNEL=chrome or msedge. Browser tests intercept
all requests and never write to the real database. Unit tests use SQL/DOM contract fakes.
They do not establish
that actual DDL, FK engines, collation or browser layout work on the target host.

Manual checks on the disposable test database:

- Create two successive years and inspect Category/Group/question ID remapping.
- Simultaneous same-year creation in two browsers; only one should succeed.
- Rename/edit/move/reorder/disable/delete in the newer year; inspect the older year.
- Verify standalone and grouped project dropdowns, inactive records and ungrouped questions.
- Create and switch years; Edit/Copy snapshots after template rename or deletion.
- Custom questions, question IDs, Section titles/descriptions, submit, Result and all dashboards.
- Desktop/mobile layout and keyboard navigation on changed controls.

Rollback: keep the additive columns/tables and all snapshots. Do NOT restore the old
unscoped bank routes once annual rows exist: they would show multiple years together.
Use a compatibility release or temporarily disable bank writes while fixing forward.
Never delete annual rows or rewrite old form/submission JSON to roll back this UI feature.
Any actual Production migration/deployment requires a separate operation outside this task.

## Release gates

- Render auto-deploys on commits to its linked branch: pushing is a deployment action.
- Confirm the database endpoint and instance fingerprints from Render's running environment.
- Forms 76, 77 and 86 remain unchanged. Their missing-date Legacy submissions use
  the compatibility policy above; existing responses remain intact. Run
  tests/browser-legacy-preview.cjs to exercise rendering/submitting with mock APIs.
- Admin authorization now uses server-side sessions; see ../AUTHENTICATION.md for the
  single-instance requirement, cookie/CSRF contract, rollout and remaining scope limits.
- Include all new runtime modules and public assets in the release; .env stays ignored.
- Keep a verified database backup and an application release compatible with yearly banks.
  Do not revert to unscoped pre-year APIs or delete annual data as a rollback.
